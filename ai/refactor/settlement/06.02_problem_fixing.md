# 06.02 Problem Fixing: Presentation State Flattening

<objective>
Fix the architecture problem described in `06_problem_presentation_state_flattening.md`.

Purpose: stop `Settlement.Presentation` from becoming the owner of every Stage 1 HUD concern, reduce cross-feature coupling, and prevent future AI/code changes from adding more unrelated fields to `Stage1HudState`.

Output: smaller owner-scoped presentation states, narrower state-builder systems, and architecture guardrails that catch new flattened cross-feature UI state.
</objective>

<scope_notes>
`ai/gdd/06-production-ready-direction.md` is about future product systems: biome taxes, base raids, caravans, outposts, and simulation layers. This 06.02 plan is not in that document and should remain refactor-only.

Additional issues found during the audit:
- `Stage1ContextPanelState` has the same flattening problem as `Stage1HudState`, but split by mode rather than only by feature owner.
- `Settlement.Presentation` has broad dependencies that make UI edits reach into unrelated feature internals.
- The project has a write-boundary guard, but no equivalent guard for presentation dependency scope or flattened cross-feature screen state.
- `ClientStage1ContextPanelStateSystem` mixes state building, interaction selection, labels, summaries, and formatting.
</scope_notes>
