# 06.02 Problem Fixing Summary

## Accomplishments

- Eliminated the monolithic `Stage1HudState` and replaced it with narrow, owner-scoped presentation resources:
  - `SettlementHudState` (objective, resources, workers, derived flags)
  - `ExpeditionHudState`, `ThreatHudState`, `RaidHudState`, `BossHudState` (Frontier)
  - `LoadoutHudState` (Loadout)
  - `ProgressionHudState` (Progression)
- Split the mixed `Stage1ContextPanelState` into explicit mode-specific states:
  - `BuildingContextPanelState` (construction site, actions, resources, progress)
  - `WorkerContextPanelState` (assignment, task, blocking reason)
- Extracted building action label/summary resolution into `BuildingActionPresentationCatalog`, removing the embedded switch ladder from the state builder.
- Replaced the flattened HUD builder (`ClientStage1HudStateSystem`) with per-feature writer systems and a composite bridge (`Stage1HudCompositeBridgeSystem`) that assembles section states for the shell controller.
- Replaced the mixed context panel builder (`ClientStage1ContextPanelStateSystem`) with ordered mode-specific systems (`ClientBuildingContextPanelStateSystem`, `ClientWorkerContextPanelStateSystem`) and a composite bridge (`Stage1ContextPanelCompositeBridgeSystem`).
- Added architecture guardrail tests (`PresentationDependencyScopeTests`) that detect new foreign logic component reads and new foreign `*.Logic` asmdef dependencies in `Settlement.Presentation`.

## Architecture Decisions

1. **Owner-scoped read models.** Every feature that owns replicated gameplay data now provides its own `IResource` HUD read model and a small client system that writes it. Settlement no longer reads `ProgressionState`, `ThreatState`, `BossEncounterState`, or `PreparedLoadoutSnapshot` directly.
2. **Composite bridge pattern.** The HUD and context panel shells use custom `ControllerEcsBridgeSystem<TController>` implementations that read all owner resources and forward them in a single `Apply` call. This avoids multiple `ControllerResourceBridgeSystem` pairs and repeated view re-renders.
3. **Mode-specific context panel states.** Instead of one nullable/flag-heavy struct, building and worker contexts have independent states. The view switches render paths based on the mode passed by the composite bridge.
4. **Presentation catalog for labels.** `BuildingActionPresentationCatalog` owns label and summary strings. The state builder only decides *which* action is active; the catalog decides how it is described.
5. **Architecture tests as guardrails.** `PresentationDependencyScopeTests` uses source scanning (no compilation) to baseline existing cross-feature presentation reads and to fail on new ones. This mirrors the existing `FeatureWriteBoundaryTests` pattern.

## Baseline Debt Remaining

- `Settlement.Presentation` still references several foreign `*.Logic` assemblies (`Buildings`, `BuildingCatalog`, `Loadout.Logic`, `Frontier.Logic`, `Progression.Logic`, `AiBots`, `Settlement.Workers.Logic`) due to controller helpers and the context panel's building interaction logic.
- `ClientBuildingContextPanelStateSystem` still performs `ClientProjection.Read<ConstructionSiteState>` and `ClientProjection.Read<ConstructionProgress>` (Buildings feature). Removing this debt requires Buildings to provide its own narrow context-panel read model.
- `Stage1ContextPanelController` still sends `DepositConstructionResourcesRequestEvent` and `BuildConstructionRequestEvent` directly. This is acceptable because the controller forwards UI intent through typed request events, not by mutating foreign state.
